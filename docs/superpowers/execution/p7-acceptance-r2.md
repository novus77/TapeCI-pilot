### 3.1 P7-06 — the reorg claim is **FALSE** as stated

The row claims: *"a `confirmed` attempt is no longer short-circuited forever… Only a
positive reorg demotes it: an unreadable node leaves the confirmation standing."*

**The code does the opposite of its own comment.** `isCanonical`
(`apps/api/src/provisioning/transactions.ts:1071-1090`) catches a failed `getBlock` and
returns `null` (`:1081-1083`), then compares `primary !== expected` (`:1087`). `null` is
never equal to the expected hash, so **an unreadable node returns `false`** — the same
answer as a real reorg. I reproduced this in isolation:

```
unreadable primary   -> isCanonical = false
unreadable secondary -> isCanonical = false
both readable        -> isCanonical = true
```

Consequence: an RPC outage **demotes every confirmed payment** to `unresolved` with
`CHAIN_REORG_PENDING`. That is precisely the false negative the comment at `:571` and the
issue-log row forbid — and it contradicts P3-12's own stated principle ("a test can never
claim agreement") and the `unavailable ≠ false` rule the whole codebase is built on.

Worse, **no test covers reorg detection at all**:

- `grep -rn "CHAIN_REORG_PENDING|reorg" tests/` → hits are **comments only**. No test
  constructs a confirmed attempt whose block later changes.
- `transactions.test.ts:34-35` — the file's own header still says *"a `confirmed` attempt
  is short-circuited and never re-read, so the §9.1 'confirmed → submitted on a later
  reorg' row is unimplemented."* The header was never updated to match the new code.
- The three `区块变化` tests (`:632,:679,:707`) all start from **`submitted`** attempts. They
  prove the *first* confirmation is gated on canonicity. They never reach the
  confirmed→reorg path.

So of P7-06's three claims: replacement recording is **real** (§3.4), cancel/replace→failed
is **derived but untested end-to-end**, and reorg detection is **implemented in the wrong
direction and untested**.

### 3.4 P7-06 replacement recording — real, but the reader is ambiguous

The writer is genuine: `recordReplacementAttempt` (`:730-765`) marks the original
`replaced` and inserts a new row carrying `replacementFor` + the same `intentId`.

However `readAttempt` (`:879-902`) selects **one** row for an intent with
`.limit(1)` and **no `ORDER BY`**, even though a replacement makes two rows share that
intent. Which row a verifier reads is therefore undefined at the SQL level. The test at
`:404` passes because it only asserts `pending`, which holds for either row — so it cannot
detect the ambiguity. The partial unique index
(`provisioning_transactions_intent_root_key`, `schema.ts:1076-1078`) correctly excludes
replacements from being roots, so this is not a correctness violation today, but the
verifier's row choice is unspecified and untested.
