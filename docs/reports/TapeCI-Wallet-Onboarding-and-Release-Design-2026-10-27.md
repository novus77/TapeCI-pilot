# TapeCI 钱包资源接入与发布闭环设计

日期：2026-10-27  
状态：产品设计草案；已结合当前代码检查，未实现新增接口，未执行购买或主网交易。  
关联：[真实用户流程审查](./TapeCI-User-Journey-Audit-2026-10-27.md)

## 1. 产品方向与本次修正

平台负责帮助用户准备发布需要的链上资源。用户连接钱包后，平台展示该钱包拥有的电路及其所属处理器编号、关联容器和准备状态；已有的直接使用，缺失的可以通过平台提供的采购或准备接口补齐。用户可以选择完整准备方案，随后在同一流程内接入 GitHub、构建、审批、发布和访问网站。

因此，上一轮“用户必须在平台之外提前准备已开启容器”的接入方式需要调整。已开启容器应是发布执行前的条件，而不是进入平台和创建项目草稿的条件。

“一整套”表示统一选择、报价、进度和交付验收；不能在尚未确认合约能力时承诺只需一笔交易或一次钱包确认。

用户已明确的需求：

- 连接钱包，或填写地址后查看对应资产。
- 展示处理器编号、电路编号，尽量直接选用，减少手工填写地址。
- 平台可以提前准备资源，并提供购买或补齐缺失资源的入口。
- 支持完整准备方案，完成首次发布所需准备工作。
- 优化不删除现有功能，同时解决上一轮发现的操作断点。

本设计采用的默认方案：优先复用已有资产；初期面向现有 X Layer 网络；平台不保管用户私钥；采购来源使用可替换适配器；没有可验证采购接口时展示真实不可用状态，不模拟购买成功。上述为设计建议，不等同于已经确认的商业规则。

## 2. 资产模型与页面用语

当前代码中的处理器是 Factory 注册的电路 NFT 合约；电路由该合约下的 tokenId 标识。页面应显示“处理器 #0 下的电路 #5”，不能仅根据处理器目录就说用户拥有某个处理器。

| 对象 | 业务含义 | 唯一标识与检查方式 |
| --- | --- | --- |
| 处理器 | 电路所属系列或合约 | chainId + factory + processor address；processorIndex 用于目录展示 |
| 电路 | 用户持有的电路 NFT | chainId + processor address + tokenId；用 ownerOf 核验当前所有者 |
| 容器 | 电路对应的账户与站点资源 | 从协议 accountOf 推导，分别检查是否部署和是否开启 |
| 发布权限 | 项目操作权限及链上临时操作授权 | GitHub/项目角色、钱包所有权和 operator session 分开判断 |
| 站点激活 | 域名绑定、有效期和网关访问 | 绑定合约状态与实际访问状态分别展示 |

电路 NFT 不应未经核验就被标注为可发布静态网站；资源准备检查还要确认相关容器和协议兼容性。电路数量、计算规格也不能直接推导成网站存储套餐额度。

## 3. 完整用户流程

1. 登录 GitHub，或先查看钱包资源；公开链上资产查询不强制先登录。
2. 连接钱包，自动读取当前地址和网络。手工输入地址进入“仅查看”模式。
3. 展示“我的电路”，按处理器分组，包含电路编号、容器、所有者核验、开启状态；项目关联仅对有访问权限的登录用户展示。
4. 用户选用现有资产；没有合适资产时进入“准备发布资源”。
5. 平台生成缺项清单与报价：需要获取电路、开启容器、激活站点中的哪些步骤，已有步骤自动跳过。
6. 匿名用户可浏览资源、目录和报价；创建可恢复任务前完成登录，默认交付钱包须通过地址控制权验证。随后确认交付钱包、商品或资源、每步费用、平台服务费、预计交易次数和后续费用，再逐步完成必要授权与交易。
7. 平台根据链上确认验收资源，显示“资源已准备”；域名可以此时激活，也可发布后激活，并分别标记状态。
8. 选择 GitHub installation、仓库、分支和构建配置，绑定选中的资源。也允许先创建项目草稿再补齐资源。
9. 完成准备检查并明确启用首次构建，选择确定的 commit；不在配置未完成时自动触发构建或付费发布。
10. 构建成功后审阅变更、费用与签名内容，审批、执行并验证发布。
11. 项目页展示当前版本、公开网址、域名有效期和可访问状态；失败则提供对应恢复入口。

用户可以从中断步骤继续。刷新页面、拒绝签名、关闭钱包均不能让已经确认的资源准备结果丢失。

## 4. 钱包资源发现

### 4.1 三种接入情形

| 情形 | 用户看到的结果 | 下一步 |
| --- | --- | --- |
| 已有电路且容器已开启 | 可选资源，显示所属处理器、电路编号及关联项目 | 直接绑定项目，检查发布授权与站点激活 |
| 已有电路但容器未开启 | “需要开启”，显示开户费用和 gas 估计 | 仅补齐开启步骤，避免重复购买电路 |
| 没有可用电路 | 明确空状态，提供资源目录和完整准备入口 | 获取电路并准备容器 |

“查询失败”“扫描中”“部分结果”和“确认无资产”必须区分；RPC 或索引异常时不能直接显示“钱包没有电路”。

### 4.2 发现与所有权核验

- Processor 列表来自可信 Factory 目录。资产候选通过已核验的索引服务或 ERC-721 转移事件索引获得。
- 不假设合约提供 tokenOfOwnerByIndex；当前 ABI 没有证明该能力。也不把遍历所有 tokenId 作为默认在线查询实现。
- 索引须处理 mint、transfer、burn，记录扫描区块和同步进度。索引滞后时可通过手工处理器/电路编号补充查询。
- 用户选择、购买完成及发布前，重新通过链上 ownerOf、accountOf、isDeployed、isOpened 核验，索引记录只用于发现。
- 资产结果带 network、observedBlock 和同步状态，处理器与 tokenId 均保留精确值，tokenId 通过字符串传输。
- 切换钱包或网络后刷新资源和准备计划；旧订单仍绑定原交付钱包，不能静默改成新账户。
- 已被其他项目使用的容器明确提示共享关系和写入影响，不直接判为不可用，也不静默复用根路径。
- 公开资源结果只包含链上信息。项目、仓库、成员及平台任务关联按现有项目权限返回；无权限的关联不返回标识或详情，也不因输入钱包地址而获得访问权限。

### 4.3 地址查询、钱包连接与权限

输入地址或钱包连接只用于发现公开资产，不证明用户有操作权限。需要将钱包绑定到登录身份时，复用现有 challenge/verify 流程证明地址控制权；链上所有者要求和项目角色仍分别核验。

现有 challenge/verify 依赖已登录身份，并非独立的钱包登录能力。默认首期沿用 GitHub 登录，再验证交付钱包；赠送到其他地址或独立钱包登录属于后续明确设计的范围。

每个页面直接支持连接、切链和更换账户，覆盖注入钱包及 WalletConnect；硬件钱包通过支持的宿主连接方式接入，需设备实测。资产查看签名不得附带购买或发布授权。

## 5. 采购与完整准备方案

### 5.1 获取来源

产品支持两类来源，但第一期是否同时开放由真实供应能力决定：

1. 协议或供应方接口：读取可用资源和当前报价，构造经过核验的购买交易或跳转到供应方购买页面。
2. 平台预备库存：平台提前准备资源，售出后交付到用户指定钱包，核验实际所有权与容器状态。

现有代码不能证明电路购买、流片服务、库存交付、退款或单笔组合交易已经存在。供应适配器必须明确自己交付的是电路 NFT、处理器相关服务还是已准备容器，不能统称“购买处理器”。“流片”若是独立商品或服务，应单独建模其规格与交付条件，不假定等于 mint。

平台预备容器即使曾开启过，也需要在交付后检查所有权、残留 operator 授权、旧站点内容及绑定关系；有遗留控制权的库存不能直接标记为可交付。该检查针对平台实际转交库存的具体场景。

### 5.2 报价单必须说明

- 供应方、商品/资源标识、网络、交付钱包及报价有效期。
- 已有资源、缺失资源和每一步交付条件。
- 商品价格、容器开启费用、域名激活费用、平台服务费、支付币种与合计。
- gas 估计、估算时点、预计交易次数；商品收费上限与交易 gas 上限分别说明。
- 哪些费用现在收取，哪些属于后续部署/续期；不把未来部署 gas 算成已支付权益。
- 支付方、交易发送方、资源接收方；默认使用用户钱包自行支付，平台代付仅在已实现对应能力时显示。
- 失败后的已交付资源、已花 gas、未执行步骤和适用退款规则；未确认退款能力时不承诺自动退款。

小额费用使用足够精度，不显示成零。报价过期、库存变化或步骤变化时，重新报价并让用户确认变化。

### 5.3 可恢复的准备任务

准备任务与部署任务分开存储：有资源准备订单不等于已经发布网站。每一步记录输入资源、报价快照、交付钱包、交易哈希、确认区块和验收结果。

步骤状态采用 waiting、awaiting_signature、submitted、confirmed、failed、skipped；submitted 时先核验原交易结果，不能因刷新或超时再次发起购买。交易被替换、丢弃或确认失败后，才进入明确恢复分支。

统一购买体验不承诺跨合约原子性。如果电路已购买、开启容器失败，保留已获得电路，重新检查并只继续开启步骤；不能再次售卖同一套完整资源。取消剩余步骤不撤销已经确认的链上操作。

## 6. 页面和接口范围

### 6.1 页面

- **我的资源**：钱包、网络、处理器分组、电路列表、容器准备状态、查询进度和刷新。
- **准备发布资源**：复用资产或选购、缺项清单、配置、完整报价及交付钱包。
- **准备任务详情**：每步进度、交易、已交付资源、失败原因和继续操作。
- **新建项目**：资源选择替代强制输入地址；保留高级手工接入入口；配置未完允许保存草稿。
- **项目概览**：准备状态、构建/发布状态、当前线上版本、公开网址、访问检查和下一步。
- **部署详情**：构建日志、变更审阅、签名摘要、执行状态、交易证据和恢复动作。

UI 延续既有 GitLab 方向：项目上下文、清晰导航、紧凑列表、状态对应的主操作。现有证据、审计、预算、比较、成员、通知和手工签名功能保留。

### 6.2 建议新增的服务边界

以下为待实现能力，不是当前已上线接口，也不预先固定 URL：

| 能力 | 输入 | 输出/约束 |
| --- | --- | --- |
| 查询钱包资源 | chainId、wallet、cursor | 电路与容器、同步区块、完整性及分页信息；公开查询不代表写权限 |
| 查询可购资源 | chainId、所需能力 | 供应来源、规格、交付条件和当前可售状态 |
| 生成准备报价 | 所选资源/商品、交付钱包、准备选项 | 缺项、价格明细、步骤、有效期与报价标识 |
| 创建准备任务 | 已确认报价、已验证会话、幂等标识 | 持久化任务，固定钱包与报价快照；本步骤不默认为付费交易授权 |
| 构造下一步交易 | 任务、步骤、当前钱包 | 经服务端核验的 chainId、to、value、data 和解释；按已验证协议/供应方接口构造 |
| 核验步骤 | 任务、步骤、交易哈希 | 服务端读取 receipt 并核验目标事件、接收者、资源和最终所有权；不能信任客户端“成功” |
| 查询/继续任务 | 任务标识 | 返回已有结果，重新核验后决定下一步，不重复购买 |
| 检查项目准备情况 | 草稿、资源、GitHub 配置 | 阻塞项、责任方、操作链接；通过后才启用构建/执行相应阶段 |

只接入外部购买页面时，平台记录 pending_external，回来后重新发现和核验资产；不能把跳转视为购买成功。供应通知需要按该供应方协议验签，并与链上或交付记录交叉核验。

## 7. 与当前实现对照

| 能力 | 本次代码检查结论 |
| --- | --- |
| 处理器目录读取、编号映射 | 已有 cpuCount/cpuAt 和 findProcessorIndex 基础能力 |
| 单个电路和容器推导、所有权与开启状态核验 | 已有 deriveContainer/inspectContainer；可复用 |
| 钱包绑定身份 | 已有 /v1/auth/wallet/challenge 和 /verify；需接入统一 UI |
| 域名绑定、费用读取和激活 | 已有组件与 API；仍需补齐当前页连接钱包等流程 |
| 项目接入 | 当前 POST /v1/projects 要求 containerAddress；草稿能力需要另行设计，不能仅去掉前端必填 |
| 容器读取 | 当前详情路由从已有项目及成员关系查找容器，不能直接充当“钱包所有资产”接口 |
| 钱包全量资产发现 | 本次检查未发现可直接复用的完整枚举接口，需要索引和公开查询边界 |
| 电路购买/流片商品/库存交付 | 当前 ABI 未包含已验证购买或 mint 方法；需要真实供应接口、合约证据及价格规则 |
| 开启容器 | ABI 已有 open/FEE，但不等于已实现完整的钱包开启页面和采购任务编排 |
| 完整准备任务与恢复 | 需要新增持久化模型和编排，不能复用部署状态冒充资源交付状态 |
| 构建日志、手动触发、失败重试 | 上轮流程检查发现缺口，仍应纳入本次闭环 |

本节为静态代码检查，不是重新验证现网合约或供应方可用性。

## 8. 实施顺序与验收

第一阶段：统一钱包连接、地址查询与身份验证；实现资源发现、现有电路选择、容器准备检查；补齐当前页钱包激活入口。

第二阶段：对接一个已核验的资源供应来源，提供缺项报价、逐步购买/开启和持久化恢复；再根据实际库存服务扩展预备资源交付。

第三阶段：打通项目草稿、准备检查、构建日志、触发/重试、签名前摘要、执行与站点访问。完善状态对应首屏和统一项目上下文。

草稿与自动构建启用状态由服务端持久化并执行约束：草稿或尚未启用的项目收到 Webhook 时，记录收到事件及未触发原因，不创建构建任务。启用后由用户选择确定的 commit 发起首次构建，后续推送才按配置触发；不自动重放草稿期间全部推送。不能仅通过前端按钮控制此行为。

关键验收场景：

1. 已有已开启资源：无需购买，直接选用，完成首次发布。
2. 已有未开启电路：只支付实际缺失步骤，正确显示接收资源与费用。
3. 无电路：完成报价、采购、资源到账核验、开启、项目配置和发布。
4. 平台库存：交付到目标钱包，确认旧授权和绑定已按交付条件处理。
5. 手填他人地址：可查看，不能据此采购授权、绑定身份或操作他人资源。
6. 发现服务部分失败：显示同步状态，不错误诱导重复购买。
7. 报价过期或账户切换：旧任务不改交付对象，新步骤重新核验与确认。
8. 购买成功、开启失败、刷新与服务重启：任务恢复，不重复付费购买。
9. 拒签、余额不足、交易 pending/替换/失败：保留进度和可执行恢复路径。
10. 构建失败、审批过期、上传失败：日志可定位，恢复动作与状态一致。
11. 发布成功但域名未激活：分别显示状态，完成激活后才确认站点可访问。
12. 注入钱包、WalletConnect、硬件宿主桥接及中英文/窄屏路径分别测试。

## 9. 开发前仍需落实的商业与协议输入

这些事项不阻塞本文设计，但会阻塞对应采购路径上线：

- 首个真实供应接口/合约及验证材料：电路购买、流片服务、库存交付分别由谁提供。
- 资源商品规格、平台收费、支付币种、交付时效及退款/售后规则。
- 当前协议对转移后容器开启状态、遗留授权和域名绑定的实际行为。
- 是否支持平台代付、折扣套餐或组合交易；未落实前按用户钱包逐步支付设计。
