# Compression Stage C1: TapeKit source integration and physical releases

Date: 2026-10-28. Branch: compression-release. Status: local source integration and immutable physical preparation verified. Production publishing remains disabled.

## Delivered

1. Exact `tapeci.pack-entry.v1` HTML descriptor, small enough for the existing atomic index.html cutover. It pins a content-addressed pack index and signed fallback setting.
2. `openPackedSite` adapter connecting the browser decoder to the original same-snapshot TapeKit file reader. Descriptor, index and objects require exact physical membership/path, status ok, verified=true, correct size and independently calculated SHA-256. A physical fallback cannot satisfy a missing object. No-hash compressed dependencies fail closed.
3. `prepareCompressedRelease` in @tapeci/release: exact copied physical bytes, strict Manifest v1, separate source/physical artifact digests, normalized addresses and a release ID derived from final physical bytes. Existing original release preparation remains available. No API worker behavior was enabled or replaced.
4. Reproducible pinned-source overlay generator. It checks official TapeKit commit/file hashes, exports tracked source only into a new directory, integrates both client/server openSite paths, reserves the adapter route, preserves native MIME/CSP/purity/error handling and builds the actual gateway distribution.
5. Source, browser and preparation regression tests plus MIT notices for the upstream-derived MIME policy.

The adapter virtualizes get only. Manifest/info/prefetch retain physical storage semantics. This milestone targets the sw-gateway client/server shells, not every viewer, extension or third-party gateway.

## Tests and independent review

- 248 focused unit/local-source-integration/original regression cases passed across 12 test files. This includes 197 original validation/Manifest/planning/cutover/verification/root-mode cases, 34 prior compression cases, 8 TapeKit wrapper cases, 5 compressed preparation cases and 4 pinned-source overlay cases.
- Chrome, Firefox and WebKit each passed seven browser journeys: 21/21 passed, no skips or flaky results. The new journey loads the actual bundled adapter plus original TapeKit fileResponse/resolvePath modules in a real browser with physical fixture data. It explicitly does not claim live RPC verification. Existing real Vite smoke remains initial UI/resources only, with external requests blocked.
- `bun run check`: lint, root typecheck and web typecheck passed.
- Feature-scoped `git diff --check HEAD`: passed. No full-network/fork suite was run in this milestone.

A fresh reviewer identified three compatibility bugs; each received a failing regression and fix:

1. `/docs` must try docs/index.html before SPA fallback, matching existing TapeKit directory routing.
2. Logical MIME must preserve native sanitization. Both overlay entrypoints now inject TapeKit's own safeContentType; the standalone adapter has a matching default.
3. Immutable-file RPC failures must retain their original error identity, allowing the native server handler's RPC explanation and Retry-After rather than misclassifying them as corrupt data.

Reviewer rechecked all three fixes and address normalization, with no remaining actionable findings in that scope. Canonical address output also has its own regression.
