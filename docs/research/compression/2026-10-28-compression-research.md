# TapeCI 前端上链压缩研究

日期：2026-10-28。状态：研究建议，尚未接入生产发布流程。

## 1. 推荐方向

采用“稳定分组压缩、按内容复用、小入口切换”。先验证 gzip，Brotli 作为候选；保留原始文件发布模式。优化目标是首次发布、后续更新和用户访问的综合成本，而非单次压缩率。

压缩位置：构建 → 原始文件检查 → 分组/压缩候选 → 运行兼容性检查 → 最终 Manifest/报价 → 审批 → 上传核验 → 切换入口。审批后禁止重新压缩或修改最终字节。

## 2. 开源参考

| 项目 | 可借鉴内容 | 边界与许可证 |
| --- | --- | --- |
| [fflate](https://github.com/101arrowz/fflate) | 浏览器 gzip/ZIP、精简解压模块、异步处理 | MIT；按需引用，测量实际回退解码器体积 |
| [Brotli](https://github.com/google/brotli) | 文本资源高压缩率 | MIT；编码耗时和浏览器支持需测量 |
| [Zopfli](https://github.com/google/zopfli) | 较慢编码换取 gzip/deflate 体积优化 | Apache-2.0；适合发布候选，先验证收益是否抵得上计算成本 |
| [zip.js](https://github.com/gildas-lormeau/zip.js) | ZIP 流式导入和读取 | BSD-3-Clause；不必把完整 ZIP 工具链装进每个站点 |
| [SingleFile](https://github.com/gildas-lormeau/SingleFile) | 自包含页面、自解压归档思路 | AGPL-3.0；页面归档不等于任意应用运行兼容；参考架构与复制代码需区分 |
| [ReplayWeb.page](https://github.com/webrecorder/replayweb.page) | 归档资源的 URL 映射、浏览器运行时 | AGPL-3.0；复杂且较重，优先研究机制 |
| [Workbox precaching](https://developer.chrome.com/docs/workbox/modules/workbox-precaching) | 内容版本、缓存复用、生命周期 | 借鉴缓存机制，不替代链上完整性核验 |

SingleFileZ 官方说明已合并到 SingleFile，不应当作独立持续维护的首选。

[TapePack](https://1-2-344.tapekit.org/) 可参考“压缩包加入口、增量与重打包比较”的产品设计。npm 查询的 `@tapepack/mcp` 版本为 0.2.4、声明 MIT，但元数据没有 repository/homepage；这不能证明整个压缩引擎已开源，也未确认独立打包接口。集成前需取得源码或格式说明，明确是否能只生成产物、由 TapeCI 统一发布。

浏览器 [DecompressionStream](https://developer.mozilla.org/en-US/docs/Web/API/DecompressionStream/DecompressionStream) 的格式支持因浏览器而异。运行时按格式检测，不能仅检测 API 存在，也不能假设所有浏览器原生支持 Brotli。gzip 基线也应具备经过验证的回退路径。

## 3. 本地真实产物实验

样本：工作区 web/dist，一份含 5 个文件的 Vite 构建，总计 370,793 字节，以 JS/文本为主。脚本使用 Node 内置 zlib，无安装、无 Actions、无链上写入。分组仅按 HTML/CSS、JS、其他资源划分，尚非依赖图分组。

| 方案 | 压缩后字节 | 字节减少 | 负载分块数，24,000 字节/块 |
| --- | ---: | ---: | ---: |
| 原始文件 | 370,793 | — | 19 |
| gzip 逐文件 | 110,004 | 70.33% | 9 |
| gzip 整包 | 110,385 | 70.23% | 5 |
| gzip 分组 | 110,282 | 70.26% | 7 |
| Brotli 整包 | 88,241 | 76.20% | 4 |
| Brotli 分组 | 88,422 | 76.15% | 6 |

整包/分组包含实验索引，逐文件结果不含路由索引，口径并非完全相同。全部结果均不含生产入口、外层索引、回退解码器、交易元数据和服务费。分块数不是总交易数，字节减少不是 gas 节省率。图片/视频站点不可套用本样本比例。

模拟给 CSS 添加一条规则后：gzip 整包的变更负载为 110,430 字节，分组为 4,185 字节，逐文件为 3,676 字节。说明整包压缩会放大小更新；这是合成编辑，未运行真实构建，尚未计入文件名哈希及引用变化造成的连锁影响。

压缩/解压往返字节一致、相同输入重复编码一致均已验证。尚未验证浏览器执行、网关解压或链上费用。

复现：`node docs/research/compression/study.mjs <build-directory> /tmp/compression-results.json`。原始记录见同目录 `2026-10-28-results.json`。

## 4. 具体设计建议

1. 分组边界保持稳定：页面入口、低频依赖、高频业务、媒体。大组可以继续拆分，组大小通过报价与加载实验确定。小站保留整包候选。图片、视频、WOFF2 等已压缩资源默认比较后再决定，避免重复压缩增加开销。不要对整个二进制包做 Base64 嵌入，编码通常增加约三分之一体积。
2. 压缩对象采用内容哈希寻址；每个版本保留完整文件映射，引用未变对象。保留构建产物原路径语义，禁止简单移除 Vite 文件名哈希。先避免依赖多层历史增量包的加载链。
3. 分开记录源产物摘要、最终索引摘要、压缩对象摘要和解压文件摘要。解压执行前验证对应的完整性。固定编码器版本、参数、路径排序和序列化方式，避免时间戳导致重复压缩不一致；缓存键含源哈希、编码器版本与参数。
4. 报价比较原始文件、逐文件压缩、分组压缩、整包压缩。纳入入口/解码器/索引、交易数、实际交易模拟、旧对象复用、首屏读取次数和解压成本。压缩无净收益时自动回退原始模式。
5. 不按简单“未被 HTML 引用”规则删除文件。动态 import、运行时 fetch、路由、Worker、WASM 和多语言资源都可能需要它们。初期保留全部文件，仅按已知构建规则明确排除。

## 5. TapeCI 接入约束

当前 `prepareVersionedRelease` 使用 releases/<releaseId>/ 路径；路径变化可能使相同内容再次上传。内容寻址复用需要显式设计新的索引/Manifest 模式，不能只在上传前追加 gzip。

当前入口改写后受 24,000 字节单次切换上限约束。解码器、索引和回退逻辑不能无预算全部内联；发布应先核验全部新对象，再切换小入口。旧版本引用的对象需保留以支持回滚。

浏览器不能把任意压缩字节当普通 JS 直接运行。需确认网关是否提供匹配的 Content-Encoding，或开发浏览器加载层。后者必须验证相对 URL、动态 import、CSS url、字体、fetch、Worker、WASM、路由刷新及 CSP。先验证 TapeKit 的 Service Worker 所有权与作用域，不能假设可以额外注册接管。Blob URL 也不能自动解决全部引用问题。

当前 validator 有路径与部分静态内容约束，但不能认定已有完整密钥扫描或归档深度扫描。需要在压缩前检查源文件，解压后复核文件路径和摘要，并限制解压体积及文件数。压缩不可绕过校验。

Next.js 服务端、API、数据库与 Worker 的运行需求不会因为压缩而消失。本方案针对可静态部署的构建产物。

## 6. 建议开发顺序与验收

- 阶段一：离线比较器。用多份真实项目及两次真实构建测量，不只用本次合成 CSS 编辑。输出总发布费用估算、变更对象和字节、解压时间/峰值内存。
- 阶段二：gzip 分组加载原型。限定支持的应用类型；在真实 TapeKit 网关、Chrome/Firefox/Safari 验证页面及动态资源，记录冷加载和失败回退；不支持的应用保持原始发布。
- 阶段三：内容寻址复用、最终签名、恢复与回滚。验证同字节不同版本复用、对象损坏阻断、部分上传失败续传、切换失败恢复、旧版本访问与回滚。
- 阶段四：加入 Brotli/Zopfli 候选。按真实全流程收益选择参数，缓存压缩结果，仅相关构建变更时计算，控制 CI 分钟数。

进入主网前的验收门槛：功能与资源不丢失；最终字节可复现；完整性核验通过；入口切换与回滚可验证；至少两次真实构建证明增量收益；报告包含加载器成本和运行兼容性。当前尚未达到这些生产门槛。
